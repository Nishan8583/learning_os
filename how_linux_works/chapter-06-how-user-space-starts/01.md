## Linux User Space Startup

### Big picture

After the kernel finishes its early initialization, it starts **`init`**, the first user-space process. From there, the rest of the system is built up.

Typical startup order:

```
kernel
  ↓
init
  ↓
essential low-level services
  ├── udevd
  └── syslogd
  ↓
network configuration
  ↓
mid/high-level services
  ├── cron
  └── printing
  ↓
login / GUI
  ↓
applications
  ├── web servers
  └── other services
```

The important transition is:

> **Kernel → init → services → applications**

User space is more modular and configurable than the kernel startup path.

---

# `init`

`init` is a normal **user-space program**, traditionally located under `/sbin`.

Its primary responsibility is to:

- Start essential services
- Stop services
- Coordinate the system's transition into a usable state

On modern major Linux distributions, **systemd** is the standard init implementation.

### Other init systems

You may encounter:

|Init|Where encountered|
|---|---|
|**systemd**|Modern Linux|
|**System V init**|Older RHEL/Debian|
|**Upstart**|Older Ubuntu|
|**runit**|Some lightweight systems|
|Custom init|Embedded systems / Android|

# Why System V init had problems

Traditional System V init essentially worked like:

```
script 1
   ↓
script 2
   ↓
script 3
   ↓
script 4
```

Each script starts a service or configures part of the system.

### Main problems

- **Poor parallelism** — boot operations generally run sequentially.
- **Difficult service management** — tracking the actual daemon/PID can be awkward.
- **Boilerplate** — startup scripts contain repetitive code.
- **Limited on-demand activation** — many services simply start during boot instead of being activated when needed.

### Key conceptual change

Modern init systems improve:

```
How services start
How services are supervised
How dependencies are represented
```

Systemd is the major implementation of this approach.

# systemd Mental Model

The most important concept:

> **systemd is not just a program that runs startup scripts. It manages a graph of units and their dependencies.**

A **unit** represents some system task.

Examples:

```
service
target
socket
mount
timer
...
```

When systemd activates a unit, it can activate the unit's dependencies as necessary.

---

# Important Unit Types

### Service unit

Represents a service/daemon.

```
sshd.service
cron.service
...
```

### Target unit

Groups other units together.

Think:

```
target
 ├── service
 ├── service
 ├── mount
 └── ...
```

### Socket unit

Represents a location where network connection requests arrive.

### Mount unit

Represents a filesystem mount.

---

# Boot = Dependency Graph

A very important distinction:

### Don't think:

```
default.target
      ↓
      A
      ↓
      B
      ↓
      C
```

### Think:

```
              ┌── A ──┐
              │       ↓
default.target ── B ──→ D
              │       ↑
              └── C ──┘
```

Systemd dependencies form a **graph**, not necessarily a simple tree.

A unit can depend on multiple other units, meaning branches can converge again.

### Boot concept

Normally:

```
default.target
      ↓
dependencies
      ↓
more dependencies
      ↓
services/mounts/etc.
```

`default.target` is normally a link to a higher-level target representing the desired system state, such as a graphical environment.

---

# systemd Does Not Simply Run Everything Sequentially

This is one of the biggest differences from traditional init.

Systemd activates units **when their dependencies/requirements allow them to become ready**, rather than following one rigid startup sequence.

It can also react to system events later and activate additional units.

```
Boot
 ↓
activate initial units
 ↓
units become ready
 ↓
other dependent units activate
 ↓
system events
 ↓
additional units activate
```

# systemd Configuration

There are two major places to remember:

```
/usr/lib/systemd/system
```

or commonly:

```
/lib/systemd/system
```

→ **Distribution-provided system units**

and:

```
/etc/systemd/system
```

→ **Local administrator configuration**

### Important rule

> **Don't modify `/usr/lib` or `/lib` system unit files when you can make the change under `/etc`.**

Why?

Because distribution-managed files can be overwritten during updates.

Prefer:

```
/etc/systemd/system/
```

for your local modifications.

---

# Find systemd's Actual Search Path

```
systemctl -p UnitPath show
```

Example:

```
UnitPath=/etc/systemd/system.control
         /run/systemd/system.control
         /run/systemd/transient
         /etc/systemd/system
         /run/systemd/system
         /run/systemd/generator
         /lib/systemd/system
         ...
```

This is useful because **systemd has multiple configuration locations and precedence matters**.

---

# Find Distribution's Unit Directories

```
pkg-config systemd --variable=systemdsystemunitdir
```

Example:

```
/lib/systemd/system
```

Local configuration directory:

```
pkg-config systemd --variable=systemdsystemconfdir
```

Example:

```
/etc/systemd/system
```

## Mental Model to Remember

For Linux startup, remember this chain:

```
KERNEL
  │
  │ starts
  ▼
INIT
  │
  │ systemd
  ▼
UNITS
  │
  ├── services
  ├── targets
  ├── sockets
  ├── mounts
  └── timers
  │
  │ dependencies
  ▼
DEPENDENCY GRAPH
  │
  ▼
SYSTEM SERVICES
  │
  ▼
LOGIN / GUI / APPLICATIONS
```

### Most important takeaways

- **`init` is the bridge from kernel startup to user space.**
- Modern Linux generally uses **systemd** as `init`.
- Systemd manages **units**, not merely sequential startup scripts.
- Units have **dependencies** forming a **graph**.
- `target` units group other units into desired system states.
- Systemd can start things when their dependencies are ready rather than following one rigid sequence.
- `/usr/lib/systemd/system` / `/lib/systemd/system` → distribution-managed units.
- `/etc/systemd/system` → local administrator configuration.
- Use `systemctl -p UnitPath show` when you need to understand **where systemd looks for unit definitions and their precedence**.
